# Running Ymer in production

This guide takes Ymer from the release bundle to a public server on one Linux VM with
HTTPS, daily backups that leave the machine, and monitoring that tells you when
something breaks. Everything runs in Docker Compose. Kubernetes is not covered yet.

For a server that only a few people reach over a private network such as Tailscale, see
[Private Vultr VM](../INSTALLATION.MD#private-vultr-vm-for-two-workspace-owners). The
backup and monitoring sections below apply there too.

| Piece | What does it | Where it is configured |
| --- | --- | --- |
| HTTPS | Caddy, with automatic Let's Encrypt certificates | `YMER_DOMAIN`, `YMER_ACME_EMAIL` |
| Secrets | Generated by `ymerctl init` into one private file | `ymer.env` (mode 600) |
| Backups | `ymerctl backup`: database dump and every stored file in one archive, optionally encrypted and copied to S3 | `YMER_BACKUP_*` |
| Restore | `ymerctl restore <archive>` | |
| Metrics | `/metrics` on the API and collab service, Postgres, MinIO and host exporters, Prometheus | `YMER_MONITORING` |
| Alerts | Prometheus rules, sent through Alertmanager to Slack, a webhook or email | `YMER_ALERT_*` |
| Dashboards | Grafana with a provisioned "Ymer overview" dashboard | `YMER_GRAFANA_PASSWORD` |
| Logs | JSON lines with a request id on every request | `YMER_LOG_FORMAT=json` |
| Readiness | `ymerctl check` lists what is still missing | |

## 1. The machine

- **Size:** 2 vCPU and 4 GB of memory hold a small team, with monitoring. Give it 4 GB
  more if people run Factory builds through Modal often. Use 40 GB of disk plus the
  files you expect to store, plus room for the local backups.
- **OS:** any current Linux with Docker Engine and the Compose plugin. Debian or Ubuntu
  can use the `.deb` package, which adds a systemd service and a daily backup timer.
- **DNS:** an `A` (and `AAAA` if the VM has IPv6) record for the name people will open,
  such as `ymer.example.com`, pointing at the VM.
- **Firewall:** allow inbound TCP 80 and 443 (and UDP 443 for HTTP/3) from anywhere,
  and SSH from your own address only. Keep 8080 (plain HTTP) and 3000 (Grafana)
  closed: they listen on 127.0.0.1 only.

## 2. Install and configure

With the `.deb` package (settings in `/etc/ymer/ymer.env`, backups in `/var/backups/ymer`):

```bash
sudo apt install ./ymer_*_all.deb          # starts Ymer on plain HTTP first
sudo ymerctl https ymer.example.com you@example.com
sudoedit /etc/ymer/ymer.env                # alerts, backups, AI, see below
sudo systemctl restart ymer
```

With the portable bundle:

```bash
tar -xzf ymer-server-*.tar.gz && cd ymer-server-*/
YMER_DOMAIN=ymer.example.com YMER_ACME_EMAIL=you@example.com ./ymerctl init
$EDITOR ymer.env
./ymerctl start
```

Both write production settings: the public URL is `https://<domain>`, cookies are
Secure, the plain port stays on loopback, the API trusts two proxies (Caddy and the
bundled nginx), logs are JSON and monitoring is on. Caddy gets the certificate on first
start and renews it by itself; it needs ports 80 and 443 reachable and the DNS record in
place.

`ymerctl https <domain> <email>` also switches an existing server to HTTPS. It keeps the
generated secrets, which lock the existing data, and changes only `YMER_DOMAIN`,
`YMER_ACME_EMAIL`, `YMER_PUBLIC_URL`, `YMER_HTTP_BIND`, `YMER_COOKIE_SECURE`,
`YMER_TRUSTED_PROXIES`, `YMER_LOG_FORMAT` and `YMER_MONITORING`. Restart afterwards.

### Settings worth changing before launch

- `YMER_REGISTRATION_ENABLED=false` closes sign-ups; add people with
  `ymerctl compose exec api flask --app wsgi create-user`.
- `YMER_AI_PROVIDER=anthropic` and `ANTHROPIC_API_KEY=...` for Claude. Workspace owners
  can also bring their own key in the app.
- `YMER_FACTORY_SANDBOX=modal` with `MODAL_TOKEN_ID` and `MODAL_TOKEN_SECRET` to run
  Factory builds for real.
- Alert receivers and backup settings, below.

### Secrets

Every secret lives in `ymer.env`, readable only by its owner (root for the package).
`ymerctl init` generates the database, storage, session and collab secrets and the
Grafana password; nothing secret is baked into the images or the compose file. API keys
you add (Anthropic, Modal, SMTP, S3) go into the same file. Keep a copy of `ymer.env` in
your password manager: the database and storage passwords in it are needed to open the
volumes, and `YMER_BACKUP_PASSPHRASE` is needed to read encrypted backups.

To rotate the session secret (signs everyone out): replace `YMER_SECRET_KEY` and
restart. The database and storage passwords cannot be changed in the file alone; they
are set inside those services on first start.

## 3. Backups

```bash
ymerctl backup                 # sudo ymerctl backup for the package
ymerctl backups                # list them
```

A backup is one archive, `ymer-backup-<UTC time>.tar.gz` (`.tar.gz.enc` when
encrypted), holding:

- `postgres.dump`: `pg_dump --format=custom` of the whole database (pages, documents,
  databases, comments, versions, accounts, Factory projects, search index);
- `files/`: every object in the MinIO bucket (uploads, images, Factory artifacts);
- `manifest.json`: time, Ymer version, file count and the dump's SHA-256.

The database is dumped first and the files copied after it, so every file the dump
refers to is in the copy (a file deleted while the backup runs may be missing; one
uploaded meanwhile may be extra). Redis holds only rate-limit counters and worker
heartbeats and is not backed up. `ymerctl update` takes a backup before pulling new images.

Settings:

```dotenv
YMER_BACKUP_DIR=/var/backups/ymer      # default: backups/ next to compose.yaml
YMER_BACKUP_KEEP=7                     # archives kept there; older ones are deleted
YMER_BACKUP_PASSPHRASE=...             # AES-256 with openssl; store it somewhere else too
# Off-site copy to any S3-compatible bucket (AWS S3, Backblaze B2, Cloudflare R2, Wasabi...)
YMER_BACKUP_S3_URL=https://s3.eu-central-1.amazonaws.com
YMER_BACKUP_S3_BUCKET=my-bucket/ymer
YMER_BACKUP_S3_ACCESS_KEY=...
YMER_BACKUP_S3_SECRET_KEY=...
```

Give the S3 key write access to that bucket or prefix only, and let the bucket expire
old copies with a lifecycle rule (30 days is a good start). Ymer keeps only
`YMER_BACKUP_KEEP` local copies and never deletes off-site ones.

**Schedule.** The `.deb` package enables `ymer-backup.timer` (daily around 03:15; see
`systemctl list-timers ymer-backup`). For the bundle, add a cron job:

```cron
15 3 * * * cd /path/to/ymer-server && ./ymerctl backup >> backups/backup.log 2>&1
```

Each run writes `ymer_backup_*` metrics, so a missed or failed backup raises an alert.

### Restore

```bash
ymerctl restore /var/backups/ymer/ymer-backup-20261128T031500Z.tar.gz.enc
```

It asks you to type `restore` (or pass `--yes`), checks the archive's checksum, takes a
safety backup of the current data, stops Ymer, replaces the database and every stored
file with the backup's, and starts Ymer again. Migrations bring an older backup up to
the running version. To restore from the off-site copy, download the archive first
(`aws s3 cp`, `mc cp` or the provider's console).

To rebuild a lost server: install Ymer on a new VM, put back the old `ymer.env` (or at
least its `YMER_BACKUP_PASSPHRASE`), run `ymerctl start` once, then `ymerctl restore`.

**Practise it.** Restore the latest backup on a spare VM once a month, sign in, open a
page and download an attachment. A backup you have never restored is a guess.

## 4. Monitoring and alerts

With `YMER_MONITORING=true` the bundle also runs Prometheus (30 days of metrics;
`YMER_METRICS_RETENTION`), Alertmanager, Grafana, node-exporter and postgres-exporter.
None of them is published to the network.

**Grafana** listens on 127.0.0.1:3000. From your computer:

```bash
ssh -L 3000:127.0.0.1:3000 you@ymer.example.com
# then open http://localhost:3000, user admin, password YMER_GRAFANA_PASSWORD from ymer.env
```

The **Ymer overview** dashboard shows service health and the last backup, API traffic,
error ratio and latency, the slowest routes, live editing connections and saves, worker
heartbeats, the search index and Factory queues, and host CPU, memory and disk, Postgres
connections and size, and stored file volume.

**Where alerts go.** Set one or more of these and restart; `ymerctl` writes
Alertmanager's configuration from them:

```dotenv
YMER_ALERT_SLACK_WEBHOOK=https://hooks.slack.com/services/...
YMER_ALERT_WEBHOOK_URL=https://ntfy.sh/your-private-topic     # any JSON webhook
YMER_ALERT_EMAIL_TO=ops@example.com
YMER_SMTP_HOST=smtp.example.com:587
YMER_SMTP_FROM=ymer@example.com
YMER_SMTP_USER=...
YMER_SMTP_PASSWORD=...
```

**What alerts.** The rules are in `monitoring/alerts.yml`:

| Alert | Fires when | Severity |
| --- | --- | --- |
| YmerApiDown | the API has not answered a scrape for 2 minutes | critical |
| YmerCollabDown | the live-editing service has not answered for 2 minutes | critical |
| YmerDependencyDown | the API cannot reach Postgres, Redis or MinIO for 2 minutes | critical |
| YmerDiskSpaceLow | less than 10% of the root disk is free | critical |
| YmerHighErrorRate | over 5% of API requests return 5xx for 10 minutes | warning |
| YmerSlowRequests | the 95th percentile of non-AI requests is over 2 s for 15 minutes | warning |
| YmerWorkerStalled | the AI or Factory worker has not reported in for 5 minutes | warning |
| YmerSearchIndexBacklog | a page has waited over 30 minutes to be indexed | warning |
| YmerFactoryBuildsWaiting | builds are queued and none has run for 30 minutes | warning |
| YmerBackupMissing | no successful backup in 26 hours | warning |
| YmerBackupFailed | the latest backup failed | warning |
| YmerPostgresConnectionsHigh | over 80% of Postgres connections are in use | warning |
| YmerMemoryLow, YmerHighLoad | under 10% memory available, or CPU over 90% for 15 minutes | warning |
| YmerTargetDown | MinIO, Postgres or host metrics are unreachable for 5 minutes | warning |

The monitoring runs on the same machine, so it cannot tell you the machine itself is
gone. Add an outside uptime check (UptimeRobot, Better Stack, Healthchecks.io and the
like) on `https://<domain>/api/health/ready`: it returns 200 when the API, Postgres, Redis
and MinIO are all fine and 503 otherwise.

### Metrics endpoints

- API: `GET /metrics` on `api:5000` (request counts and latency per route, dependency
  status, queue depths, worker heartbeats, account totals). It is outside `/api`, so
  the public nginx answers 404 for it. Set `YMER_METRICS_TOKEN` to require a bearer
  token as well.
- Collab: `GET /metrics` on `collab:1234` (connections, loaded documents, saves, failed
  saves, refused connections).

## 5. Logs

`YMER_LOG_FORMAT=json` writes one JSON object per line from the API and workers,
including an access line per request with method, route, status, duration and client
address. Caddy logs JSON too. Every response has an `X-Request-ID` header; Caddy assigns
it, nginx passes it on and the API logs it, so a failing request a user reports can be
found with:

```bash
ymerctl logs api | grep <request id>
```

Docker keeps the logs per container. To ship them elsewhere, point Docker's logging
driver at your system (journald, Loki, CloudWatch, ...) in `/etc/docker/daemon.json`,
and cap local logs there as well:

```json
{ "log-driver": "local", "log-opts": { "max-size": "50m", "max-file": "5" } }
```

## 6. Before you launch

```bash
ymerctl check
```

It checks the settings file's permissions, HTTPS, cookies, secrets, DNS, sign-up mode,
the AI and Factory settings, backup age, encryption and off-site copies, whether alerts
have a receiver, that every service runs and is healthy, and that
`https://<domain>/api/health` answers with a valid certificate. Fix every `FAIL` line;
`WARN` lines are choices to make on purpose.

Then:

1. Sign up (or create the first account) and close sign-ups if the server is private.
2. Run `ymerctl backup`, then restore it on a spare machine once.
3. Stop the collab service for three minutes (`ymerctl compose stop collab`) and check
   that the YmerCollabDown alert reaches you; start it again with `ymerctl start`.
4. Add the outside uptime check.

## 7. Upgrades

Download the new bundle or package. For the bundle, copy `ymer.env` into the new folder
and run `ymerctl update` there; for the package, `sudo apt install ./ymer_<version>_all.deb`.
`update` backs up first, pulls the new images, applies migrations and restarts. To go
back, install the previous version and restore the backup taken before the update.
